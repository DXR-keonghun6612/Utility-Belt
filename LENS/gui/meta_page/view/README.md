# gui/meta_page/view/

Dataset_Meta 뷰어 = 메인 본문. 3-pane — 좌 stem 목록 · 가운데 (params·데이터·객체) 트리 · 우 데이터 뷰어.

---

## 구성

- 좌 `Stem_list` — **3-버킷 상태 뱃지(작업/검수/보류)**. 우클릭 = 현재 상태가 아닌 **각 상태로 보내기**·삭제,
  더블클릭 = 팝아웃. 뱃지·카운트·메뉴는 `Dataset_Meta.CATEGORIES` 기준 제네릭이라 상태가 늘어도(예: skipped)
  `_BADGE` 한 줄만 더하면 된다. 목록 자체는 meta 를 모른다 (표시·신호·갱신만). 채울 때 **카테고리
  순서(`CATEGORIES`)는 유지하되 카테고리 안은 stem 이름 오름차순**으로 정렬한다(전이로 순서가 안 뒤섞이게).
- **전이/삭제 후 포커스**(`_next_focus`) — 포커스는 대상을 따라가지 않고 소스 카테고리에 남는다: ① 선택
  중 가장 작은 순번의 한 칸 앞, 없으면 ② 가장 큰 순번 +1(한 칸 뒤). 둘 다 없으면(그 카테고리가 통째로
  비면) ③ **전이**는 이동한 곳으로 따라가고, **삭제**는 목적지가 없으니 다음 카테고리(뒤 우선, 없으면
  앞)로 옮긴다(목록이 통째로 비면 포커스 없음). 작업 **전** 목록에서 대상 stem 을 잡아 `_focus_after` 에
  담고 다음 `load` 가 일회성으로 소비한다(`keep` 덮어씀).
- 가운데 = **세로 3단 접기(`Collapsible`) 트리** — params(dataset-wide) · 데이터(선택 stem) · 객체(선택 stem).
  **같은 재귀 렌더러 `Node_tree` 를 scope 로 세 번 쓴다**(`all`/`leaves`/`objects`). 데이터모델은 하나
  (재귀 `Data_Ref`)지만 **표현 축이 다르다**: raster leaf(`데이터`)는 체크해서 합성하고, 객체(`객체`)는
  골라서 조준·편집한다. `Node_panel` 이 각 트리에 역할별 추가/삭제 툴바를 얹는다(데이터=`+데이터`,
  객체=`+객체`/`+속성`). **객체 툴바는 storage 추가를 안 내놓아** "객체는 payload-free"(geometry 는
  stem 레벨 segment 한 장)가 UI 구조로 강제된다.
- 우 `Data_view` — **체크된 raster 합성 캔버스 + 인스펙터**. 무엇을 어떻게 **그리나**는 타입별 레지스트리
  [`gui/viewer`](../../viewer)가 알고(core 의 `HANDLER_REGISTRY` 와 짝), 어떻게 **고치나**는
  [`gui/editor`](../../editor)의 `Image_editor` 가 안다 — **앱에 하나**라 노드를 고르면 그 대상으로
  **조준**만 바뀐다. 무엇을 겨눌지는 **구조**가 정한다(객체 → 프레임의 segment 에 그 라벨 = obj_id+1,
  mask leaf → 그 라스터 자체). id_map 은 별도 패널 없이 params 트리의 일반 데이터로 함께 보이고,
  `class_id` 를 고를 때만 view 가 id_map 후보를 뷰어에 넘긴다.

  **`Data_view` 가 두 계층의 통역이다** — 뷰어는 트리를 모르고 편집기는 store 도 트리도 모르므로, 조준
  대상을 고르는 것도(`Target`), 캔버스에서 클릭한 좌표에 무엇이 있는지 답하는 것도(`picked` → 그 점을
  품는 bbox 의 객체, **겹치면 작은 상자가 이긴다**) 여기 산다.

- **캔버스에서 객체 고르기** — 보기(`V`) 모드에서 상자 안을 클릭하면 그 객체가 트리에서 선택되고, 조준이
  옮겨간다(선택된 객체가 화면 밖이면 뷰가 따라간다). **Shift+클릭은 선택을 토글**한다 — 더하고, 이미
  고른 것을 다시 누르면 뺀다. 그렇게 모은 것들을 `M`(⧉ 병합)으로 바로 합친다. 라벨링 중 손이 트리로 가지
  않게 하는 게 요점이라, **빼는 길이 없으면** 잘못 집었을 때 처음부터 다시 골라야 한다.

- **단축키의 소유자는 "무엇을 아는가"로 갈린다** — 도구·이력(`V/R/D/E`·`B/P/C/F`·`Ctrl+Z/Y`·`[`·`]`)은
  편집기가 자기 도구 선언에서 만들고, store 를 불러야 하는 것들(`0`–`9` 객체 선택 · `A` 추가 ·
  `Delete` · `M` 병합 · `Ctrl+S` 저장 · `Ctrl+R` 되돌리기)은 **`Meta_view` 가 건다**. 편집기에 store 를
  들려주면 편집기가 다시 store 에 묶여 재사용이 안 된다(옛 `Stem_editor` 가 그랬다).

## 상태 전이 = 백그라운드 (Move/Delete)

상태 전이·삭제는 **대량 여부와 무관하게 항상 백그라운드**로 돈다 — `Meta_view` 는 요청만 올리고
(`transition_requested`/`remove_requested`), 상위(app `Meta_ops`)가 워커로 `meta.Move`/`meta.Delete` 를 돌리며
진행바에 표시하고 **그동안 `Meta_view.set_editable(False)` 로 편집만 잠근다**(워커가 데이터를 변형하는
동안 편집 끼어들기 방지). 뷰 전체를 얼리지 않으므로 stem 목록 클릭·이미지 보기·줌은 그대로 되고,
잠기는 건 수정 경로뿐이다 — 전이/삭제 우클릭 메뉴, 데이터/객체 트리의 추가/삭제, 캔버스의 mask/bbox
편집, 인스펙터의 인라인 값 편집. `set_editable` 은 `Stem_list`·데이터/객체 `Node_panel`·`Data_view`
(→`Image_editor.set_locked`)로 전파한다.

완료 후 목록 재동기화는 **한 번의 `refresh()`(O(n))** 로 한다 — stem 마다 증분 갱신(`update_state`)은
리스트 전체 재스캔 + 재번호라 O(n²)라서 2만 건이면 폭발했다(과거 "응답 없음"의 실체 = 파일 이동이 아니라
이 목록 재그리기였음). `update_state`/`remove` 는 단일 항목 편집(편집 저장 등)에만 쓴다.

## 저장은 명시적이다 — 취소는 **되돌리기가 아니라 다시 읽기**

편집(붓질·상자·객체 추가/삭제/병합/인라인 값)은 **메모리에서만** 일어난다. 디스크는 `[저장]`(`Ctrl+S`)
이 누를 때까지 마지막 저장 시점 그대로고, `[되돌리기]`(`Ctrl+R`)는 그 시점으로 **한 번에** 돌아간다
(`Pipeline.Reload` — 정본을 디스크에서 다시 읽는다).

그래서 객체 삭제에 undo 스택이 필요 없다. 지웠다가 아니다 싶으면 **저장하지 않고 다시 읽으면 된다** —
편집 하나하나를 되돌리는 것보다 그게 실제로 쓰는 방식이다. (캔버스 안의 붓질·상자는 여전히 `Ctrl+Z` 로
잔손질한다 — 이력의 단위가 라스터라 그건 편집기가 든다.)

**언제 디스크에 쓰나는 payload 가 가른다.** 객체는 payload-free 라(geometry 는 stem 레벨 segment 한 장)
더하고 지우고 합치는 게 전부 메모리에서 끝난다 — 그래서 미룰 수 있다. 반면 **데이터 leaf 추가·삭제는
파일을 낳거나 지우므로** 미룰 수 없고, 사이드카도 그 자리에서 맞춘다(안 그러면 없는 파일을 가리키는
서술자가 남는다). `Node_panel` 의 확인 문구가 이 차이를 말한다.

## Pipeline 경유 — 라이프사이클은 store 소유

호출 측이 `meta.*` 를 직접 부른다 — 상태 전이 = `meta.Move(…)`, 삭제 = `meta.Delete(…)`, 편집 저장 =
`meta.Save(stem)` (그 item 사이드카만; params 편집은 전체 `Save()`).

**객체 편집 둘은 라벨맵을 함께 받는다** — 캔버스에 뜬 **그 배열**(`Data_view.segment_node()`)을 넘긴다.
store 가 디스크에서 다시 읽으면 아직 저장 안 한 붓질을 덮어쓰기 때문이다. 둘 다 **메모리만** 고치고
디스크엔 안 쓴다(위 참조).

- **객체 삭제 = `meta.Remove_object(stem, obj_id, segment)`** — 컨테이너 pop **+ 그 obj 의 segment 라벨 0**
  을 함께 한다(store 소유). 정본은 per-obj mask 를 안 들고 frame-level segment 한 장(픽셀=obj_id+1)에
  담으므로, 컨테이너만 지우면 라벨이 유령 mask 로 남기 때문이다(라벨맵을 안 넘기면 **터진다** — 조용히
  유령을 남기느니). **빈 자리는 구멍으로 둔다** — obj_id 재부여·압축은 `Order_objects`(process)의 몫이고,
  편집은 정합만 지킨다. 그래서 데이터 leaf 삭제(`Delete_node`)와 객체 삭제(`Remove_object`)를 트리가 가른다.
- **객체 병합 = `meta.Merge_objects(stem, into, others, segment)`** — 객체 트리만 **다중선택**(트리에서
  Ctrl/Shift, 캔버스에서 Shift+클릭 토글)이고, `⧉ 병합`(`M`)이 고른 것들을 하나로 합친다. 라벨맵은 픽셀당
  라벨이 하나라 배타적이므로 "합친다" = **흡수될 라벨들을 생존자의 라벨로 다시 칠하기**(= mask 합집합,
  겹침 없음)이고, bbox 는 **그린 박스들의 합집합**이다(mask 에서 되짚지 않는다 — bbox 가 진실이다).
  생존자는 **가장 작은 obj_id** 라 그 `class_id` 가 이기는데, 그걸 **확인 다이얼로그가 말한다** — store 가
  조용히 고르면 어느 class 가 이겼는지 모른 채 넘어간다. 다중선택이어도 **조준은 current 하나**다.

## 객체가 성립하는 조건 — 라벨맵의 자기 자리

객체는 payload 가 없다. 그러니 **라벨맵(`segment`)에 자기 라벨이 있어야만 객체다.** 편집 중엔 아니어도
되지만(`+ 객체` 는 빈 채로 나온다), **저장(`Order`)이 그 조건을 강제한다** — 라벨을 못 받은 객체는
떨어져 나간다. 라벨을 찾는 근거는 **bbox** 라서(`Order_by_center` 의 self-heal), *mask 는 칠했지만 bbox 를
안 그린* 객체도 사라진다. 데이터가 없어지는 일이라 `[저장]` 이 **몇 개 지웠는지 알린다**.

그래서 편집과 저장의 역할이 갈린다 — **편집은 정합**(라벨과 컨테이너를 함께 옮긴다), **저장은 정돈**
(구멍 압축 + 유령 제거).

- 저장(`_flush`)은 대기 중인 라스터를 `meta.Route`(payload write) → 그 자리에 다시 꽂고, 사이드카를
  `Save` 한다. 대기 라스터는 캔버스 편집만이 아니라 **객체 삭제·병합이 고친 라벨맵**도 포함한다
  (`Node_panel.raster_edited` → 같은 길). meta 정체성이 바뀌면(`set_pipeline`·`Reload`) 트리를 다시 로드한다.
