# core/analysis — 데이터가 스스로 나뉜 단위(type) 위에서 class 를 검증한다

"분석"이 아니라 **검증 겸 제안**이다. 표본이 그냥 들어오고 그것들이 뭉친 덩어리를 `type` 이라 부른다.
`class` 는 그 위에서 **읽히는 값**이다 — 라벨이 데이터와 맞는가, 두 class 가 이 데이터로 갈리는가.

진입점·파일별 역할은 [`__init__.py`](__init__.py). 여기는 **왜 이렇게 갈렸나**만.

## class 는 축이 아니다

옛 구조는 class 안에서만 갈랐다(`split_class` 가 class 하나만 봤다). 그런데 묻고 싶은 것이
**class 정의가 맞나** 였으므로 class 를 전제로 class 를 검증하는 순환이었다. 그래서 class 사이를
보는 물음은 구조 밖에서 따로 계산해 붙여야 했다.

실측이 그 위에 얹혔다 (64,336 표본 · `radial_rle`):

| 잰 것 | 값 |
|---|---|
| 표본간 거리 ÷ 노이즈 하한 (같은 class 안) | 중앙 **1.5** — 거리의 대부분이 촬영 흔들림 |
| 라벨 ↔ 데이터 1-NN (class 사이) | **86.0%** |

**class 안은 노이즈고 class 사이는 신호**인데 가르기를 노이즈 쪽에 세워 두었던 것이다.

지금은 `class` 가 obj 에 붙은 정보일 뿐이라 [`cluster.py`](cluster.py) 에 한 번도 안 나온다.
라벨을 고쳐도 재군집이 일어나지 않는다 — 바뀌는 것은 집계뿐이고 그건 저장하지 않는다.

## 네 가지 정의

- **`type` = 이 데이터로 더 못 가르는 최소 단위.** 임계는 손잡이가 아니라 분해 한계다.
  여러 class 가 한 type 에 드는 것은 버그가 아니라 **결과**다.
- **`type id` 는 계산 결과지 영속 식별자가 아니다.** 데이터가 늘면 갱신된다. 사람의 결정은
  **class 라벨로** 남으므로 type 변동은 정합성이 아니라 재계산 **비용** 문제다.
- **`no_label` 도 하나의 class.** 라벨 유무가 배정에 영향을 주지 않는다.
- **`outlier` 는 상태가 아니라 거리다.** 플래그가 없다 — `index` 에 남긴 `d(표본, 중심)` 이 크면
  그것이 곧 고립이다.

## feature 와 잣대 — 저장하는 것과 재는 것

둘은 **수명이 다르므로** 갈라 든다.

| | 무엇 | 어디 | 고치면 |
|---|---|---|---|
| **feature** | 정본에서 뽑은 측정값 | 디스크 | **재추출** |
| **잣대(gauge)** | 그 feature 를 접어 만든 비교 좌표 | 저장 안 함 (config) | 다시 접기만 |

그래서 **계약도 절반씩 따로 쓴다.** `features` 는 추출만이 쓰지만 `gauges` 는 **버킷을 열 때마다
config 를 따라간다**(`store.Set_gauges`, 값이 같으면 안 쓴다). 한 번에 쓰면 config 에 축을 더해도
6만 표본을 다시 뽑기 전엔 화면에 안 뜬다 — 접는 식만 바뀌었는데 추출을 다시 도는 건 갈라 둔 이유를
무너뜨린다. 반대로 저장 안 된 feature 를 가리키는 잣대는 **묶기 전에 막는다**(조용히 빠지면 체크해
둔 축이 사라져도 화면은 성공이라 말한다).

**잣대 = 도메인마다 하나.** 표본끼리의 거리를 그 좌표에서 재고 type 을 거기서 가른다 —
반경 `k` 는 그 잣대의 눈금이다. 위 계층(store·화면)은 잣대를 **도메인 이름으로만** 만나고,
그 값이 파일 그대로인지 접은 것인지는 `extract` 안에서 닫힌다.

radial 이 그 이유다. 저장은 `radial_rle` `(NT, 8)` 하나고, 재는 잣대는 **둘**이다:

```
radial_signed    Σ(부호×슬롯) = 2·살합 − 외곽r     구멍까지 담은 양
radial_outline   rle.sum(-1)  = 외곽r              실루엣
```

**`radial_rle` 자체는 축이 아니다.** 슬롯 배치까지 보면 광선이 구멍을 스칠 때 밴드가 하나 늘어
슬롯이 통째로 밀리고 값이 계단으로 뛴다 — 도넛이 하나도 안 붙던 원인이 거기였다(실측 배정률
0.0% / outline 97.0%). 접기는 그 불연속을 없앤다.

### 왜 한 도메인 `(NT, 2)` 로 안 묶었나

셋을 세 도메인으로 두지 않는 이유와 **둘을 한 도메인으로 묶지 않는 이유는 다르다.**

셋은 직교가 아니라 같은 값의 노이즈 수준 셋이라(`부호합 = 2·살합 − 외곽r` 로 대수 종속) type 셋이
뜻이 없다. 둘은 **상보**다 — 합쳐야 `(살합, 외곽r)` 이 나온다. 그리고 묶으면 둘 다 깨진다:

- **정규화 상수가 도메인당 스칼라 하나**라 두 채널이 같은 std 로 나뉜다 → 거리에서 각 채널의 몫이
  그 채널의 **원 분산에 비례**한다. 대등하게 보려던 것이 조용히 가중이 된다.
- **노이즈 바닥이 다른데 `k` 를 하나만 줄 수 있다** (도넛÷솔리드 최근접비 signed 2.45 · outline
  0.89). 실제로 같은 `k=0.05` 로 돌리면 과분할 정도가 다르다 (`temp/smoke_gauge.py`: signed 8
  type / outline 6 type).
- 불변식이 "슬롯 1의 30px 과 슬롯 3의 30px 이 같은 뜻" 인데, signed 의 30px 과 outline 의 30px 은
  단위만 같고 **교환 가능하지 않다**.

갈라 두면 **불일치가 읽힌다**: `outline` type 은 같은데 `signed` type 이 다르면 "실루엣은 같고
구멍이 다르다" 다. 원래 하려던 오검출 검사가 그것이다.

### 그림은 원본을 읽는다

잣대는 구멍 정보를 접어 버리므로(`outline` 은 꽉 찬 원반으로, `signed` 는 극좌표 곡선조차 아니라
채널 그림으로 나온다), 사람이 형상을 볼 때는 `store.Features` 로 **원본 RLE** 를 읽는다.
type 중심만은 잣대 좌표의 평균이라 접힌 채인데, 그 차이가 곧 **잣대가 버린 정보**라 나란히 보이는
편이 낫다.

## 도메인은 직교다

도메인마다 **따로** 가른다. 표본 하나는 도메인 수만큼의 type id 를 갖고 그 조합이 서명이다.

한 좌표로 이어 붙이지 않으므로 도메인 간 가중이라는 물음 자체가 없어졌다(옛 `axis_weights` 가
그걸 정하려던 자리다). 그리고 "크기로는 갈리는데 형상으로는 안 됨" 이 별도 진단이 아니라
**구조에서 바로 읽힌다** — `area` 의 type 은 갈리는데 `radial` 의 type 은 같은 상태로.

**도메인 = scale 을 공유하는 채널 묶음** (불변식). 그래서 정규화 상수가 **도메인당 스칼라 하나**인
것은 타협이 아니다. 채널끼리 scale 이 다른 도메인이 있다면 고칠 것은 정규화가 아니라
**도메인 분할**이다 — `radial_signed` 와 `radial_outline` 이 갈린 것이 그 적용례다.

### 종합 판정 — 축 label 을 읽는다

축마다 따로 가른 뒤, 표본의 **축 label 조합**을 종합 type 으로 삼는다(`cluster.join`, 자리 이름은
`JOINT`). **거리를 다시 재지 않는다.**

층마다 묻는 것이 다르기 때문이다:

| 층 | 무엇을 묻나 | 무엇으로 답하나 |
|---|---|---|
| 잣대 | 이 표본들이 **이 좌표에서** 같은가 | 표본 상호 최근접 → 연결 성분 |
| 종합 | 축들이 **서로 어긋나는가** | 축 label 을 그대로 |

한때 종합에서 type 중심끼리 다시 이웃을 재 봤다. **축이 갈라 놓은 것이 도로 붙었다** — 종합 type
하나가 outline type 17개를 삼켰고 그 17개의 최다 class 는 `151` 과 `219` 로 서로 달랐다. 같은 데이터로
같은 질문을 두 번 하면 두 번째 답이 첫 번째를 덮는다.

합집합(한 축에서라도 같으면 같다)도 아니다. `radial_outline` 은 도넛과 원판을 구분 못 하는 게
정상인데(외곽이 같다) 그 "같다" 를 받으면 `radial_signed` 가 찾아낸 구멍 차이가 지워진다.

#### 쪼갠 뒤, 자의적인 경계는 도로 붙인다

조합을 그대로 두면 잘게 부서진다 — 실측으로 종합 type 의 58%가 "outline 은 같은데 signed 가 갈랐다"
였고 그 조각의 상당수가 한두 건이었다. signed 가 틀린 게 아니라 **그 둘의 경계가 자의적**이었다:
두 type 이 서로 이웃이면 그 사이 선은 데이터가 그은 게 아니라 연결이 한 번 끊긴 자리다.

그래서 **모든 축에서 같거나 이웃**인 조합끼리 잇는다(`cluster.type_neighbors` → `_merge_cells`).
한 축이라도 멀면 안 붙는다 — 그 축이 실제로 가른 자리다. 연결 성분이라 **전이적**이고, 그 사슬이
축을 건너뛸 수도 있다. 그건 약점이 아니라 강점이다 — 경계가 자의적인 자리를 따라 구조가 이어져
있다면 그것이 하나의 덩어리인 게 맞다.

| | type | 순도 | 순수 | 1건 | 최대 |
|---|---|---|---|---|---|
| 조합 그대로 | 1,585 | 88.5% | 69.8% | 53 | 2,548 |
| **모든 축 같거나 이웃** | 832 | 88.1% | 66.8% | 22 | 2,886 |

한때 "**딱 한 축만** 다를 때만" 으로 조였다. 모든 축을 열었더니 전부 한 덩어리가 됐기 때문인데
(순도 5.1%), 원인은 축 수가 아니라 **기권이 다리가 된 것**이었다 — `(5,⊥)` 가 `(5,3)` 과도 `(5,7)`
과도 이어졌다. `impute` 가 그 구멍을 막으면서 브레이크를 뗄 근거가 섰고, 떼도 순도가 0.1pp 만
움직인다. 실측으로 번지지도 않는다(한 종합 type 이 품은 축 type 수 중앙 2).

**반대 방향(더 촘촘히 쪼개기)은 안 한다.** 종합 type 안에서 `k` 를 0.7배로 줄여 다시 봤더니 3건
이상 조각의 순도가 85.8% → 87.1% 로 1.3pp 오르는 동안 **4,042건이 1건짜리로 흩어졌다** — 노이즈
바닥을 넘은 것이지 구조를 찾은 게 아니다. 쪼개는 일은 축이 이미 한다.

#### 기권한 축은 **메운다** — 비우지도, 막지도 않는다

표본이 한 축에서 `POOL` 이면 그 조합은 남과 견줄 수 없다. 셋 중 하나를 골라야 했고, 앞의 둘은 실측으로
깨졌다:

| 처리 | 결과 |
|---|---|
| 거부권 — 한 축이라도 기권이면 보류 | 배정 76.2% (메우기 전 89.7%) |
| 통행증 — 할 말 없으니 통과 | `(5,⊥)` 가 `(5,3)`·`(5,7)` 을 잇는 **다리**가 되어 순도 5.1% 로 붕괴 |
| **메우기** — 다른 축이 후보를 좁히고 자기 축 거리가 고른다 | 1건 type 85 → 10, 순도 88.4% 유지 |

메우기(`cluster.impute`)의 규칙은 두 줄이다:

```
후보   다른 축에서 나와 같은 type 인 표본들이, 이 축에서 받은 type
선택   그중 자기 축 중심까지 가장 가까운 것 (impute_bound 밖이면 안 고른다)
```

경계(`impute_bound`)를 두는 이유 — 풀어 버리면 1건이 4까지 줄지만 순도가 88.1% 로 빠진다. 멀리 있는
것까지 억지로 붙인 대가다. 경계 밖에 남은 것이 **진짜 고립**이고, 보류 자리가 살아 있어야 그걸 읽는다.

**메운 값은 축의 답을 안 고친다.** 축 화면은 여전히 "모른다"고 말한다 — 문턱을 넘어 인정한 것과
추정으로 붙인 것을 한 자리에 두면 축이 자기가 모른다고 한 것을 아는 척한다. 사람이 그 추정을 보고
맞다고 판단하면 **[메움 전파]** 로 축에 앉힌다(`group.propagate`) — 재군집 없이 붙이기만 하고,
그 축의 통계·거리를 함께 고친다.

그래서 **종합은 자기 장부를 든다**(`store.Set_joint`). `index.types` 에는 잣대가 인정한 값만 남고,
배정·구성·메운 자리는 종합 params 한 장에 모인다. 수명도 다르다 — 축을 다시 가르면 종합은 통째로
다시 나온다.

#### 1건짜리 종합 type 은 고립이 아니다

`min_members` 를 종합에서 **다시 걸지 않는다** — 문턱은 잣대가 이미 지켰다. 조합이 1건이라는 건 그
표본이 외톨이라는 뜻이 아니라 **그 조합을 가진 표본이 하나**라는 뜻이다. 메우기 전 실측 554개 중
215개가 두 축 모두 크기 3+ 인 type 소속이었고, 그중 27개는 두 축의 최다 class 가 아예 달랐다 —
오검출 후보 그 자체다.

`k` 탓도 아니다. 오히려 `k` 를 키우면 는다(0.04 → 0.35 에서 8 → 135) — 배정이 늘면서 마지막에 붙는
변두리 표본이 그대로 단독 조합이 되기 때문이다. 화면은 그것들을 **[단독]** 한 줄로 모아 둔다.

**종합에는 좌표가 없다.** 중심·퍼짐·근접 그래프·해상도 슬라이더가 전부 축에서만 정의된다. 형상은
그릴 수 있지만(멤버가 정해져 있으니 원본을 평균한다) **어느 잣대로 그릴지는 사람이 고른다** —
화면의 [형상 축].

#### 서명은 게이지마다 — 하나만 바꾸면 하나만 돈다

`domain_signature` 가 해싱하는 것은 **그 게이지의 입력뿐**이다(`cluster.gauge_params`: 거리 상한 ·
이웃 수 · 승격 문턱 + 구성원 명단). 그래서 `radial_outline` 의 `k` 를 만져도 `radial_signed` 는 안
돈다. 한때 `min_members` 만 전역이라 그 하나를 만지면 안 건드린 게이지까지 전부 다시 돌았다 —
지금은 셋 다 게이지별이고, 손잡이를 더할 때 `gauge_params` 한 곳만 고치면 서명이 따라온다.

**종합 서명 = 축 서명들 + 종합 자기 설정**(`joint_signature`: 메우기 한계 · 병합 여부). 축이 안
바뀌면 label 도 안 바뀌므로 축 서명이 그 사실을 대신 답한다 — label 배열을 통째로 해싱하던 자리인데
6만×축 을 매번 도는 비용이 얻는 것에 비해 컸다.

**축을 다 켤수록 좋아지지 않는다.** 축마다 자기 기권이 있어 그 합집합이 커진다. 그래서 처음 켜는
것은 **config `gauges:` 에 적힌 잣대뿐**이다(`Gauge_Spec.declared`) — config 에 적었다는 것이 곧
"이걸로 보겠다" 는 선언이다. 사람이 켜고 끈 것은 레시피에 남아 다음에 이긴다.

## 묶기 — 구(球)를 버렸다

`k` 안에 든 것을 중심에 붙이던 방식은 **class 를 구로 감쌀 수 있다**고 전제한다. 실측에서 그 전제가
깨졌다 (표본 10,000 · class 134):

| | r95 (class 안쪽 퍼짐) | 가장 가까운 남 |
|---|---|---|
| 중앙 | 0.139 | 0.178 |
| 최대 / 최소 | 1.043 | 0.013 |

`r95 < 가장가까운남` 인 class 가 **39% 뿐**이고, 90% class 를 담는 `k` 구간이 아예 **비어 있다**
(`[0.517, 0.031]`). 그래서 `k` 를 올리면 순도가 무너지고 내리면 안 붙는다:

| | `k` | 배정 | type | 순도 | 최대 type |
|---|---|---|---|---|---|
| 구 | 0.08 | 88.2% | 193 | 76.4% | 560 |
| 구 | 0.30 | 99.5% | 61 | **37.6%** | **5,609** |
| 이웃 그래프 | 0.08 | 79.5% | 212 | 88.0% | 396 |
| 이웃 그래프 | 0.15 | 85.5% | 237 | 87.8% | 396 |

**feature 는 멀쩡했다** — 1-NN 이 같은 class 인 비율 87.6%. 국소 정보는 충분한데 모델이 안 맞았다.
부푼 type 도 병합 폭주가 아니었다: `k=0.15` 최대 type(1,615건)은 중심까지 최대 0.222 · RMS 0.108
≤ `k` 로 규칙대로였고, 그 공 안에 class 31 개가 실제로 들어 있었을 뿐이다.

지금 규칙은 둘이다:

```
간선   서로가 서로의 이웃 목록에 있고 거리 ≤ k     (**상호** 최근접)
type   그 간선으로 이어진 연결 성분 (min_members 미만은 대기 풀)
```

상호성이 사슬을 끊는다 — 촘촘한 덩어리 옆에 붙은 표본은 자기 쪽에서만 그 덩어리가 이웃이고
덩어리 쪽에서는 자기들끼리가 더 가까우므로 간선이 안 생긴다.

**88% 가 이 데이터의 천장이다** (1-NN 과 같은 값). 남은 12% 는 묶기 실패가 아니라 class 라벨을
의심할 자리고, 이 도구가 원래 찾던 것이 그것이다.

### 잣대마다 값이 둘 — `k` 와 이웃 수

둘 다 잣대에 붙지만 **이유가 다르다.**

| | 무엇을 정하나 | 왜 잣대마다 |
|---|---|---|
| `k` (거리 상한) | 쌍을 이을지 말지 | **축척**을 탄다 — 1° 돌리면 `radial` 은 프로파일이 밀리는데 `area` 는 거의 안 변한다 |
| 이웃 수 | 몇 번째 이웃까지 볼지 | **밀도**를 탄다 — 2채널 `area` 는 값이 겹치고 512채널 `radial_outline` 은 흩어진다 |

`k` 는 구 방식 때만큼 민감하지 않다. type 의 **크기**가 아니라 **이을지 말지**만 정하기 때문이다
(0.08 ↔ 0.15 에서 순도 88.0% ↔ 87.8%). 바닥은 여전히 **노이즈 하한**이고, 그보다 작게 잡으면
원리상 못 가르는 것을 가르게 되어 부서진다.

하한은 **참고선이지 파라미터가 아니다.** 계산 경로에 안 들어가므로 하한을 못 재는 도메인이
들어와도 시스템이 멈추지 않는다.

## 상주는 도메인 하나치

계산 전체가 [`cluster.fit`](cluster.py) 하나다. 네 걸음이고 전부 순수 함수다:

```
knn           표본마다 최근접 neighbors 개          (블록으로 끊는다 — 전체 거리 행렬은 n²)
mutual_edges  서로가 서로의 이웃이고 거리 ≤ k
components    연결 성분이 type (min_members 미만은 대기 풀)
stats_of      결과를 충분통계 (n, Σx, Σ‖x‖²) 로 요약
```

충분통계는 이제 **묶기의 재료가 아니라 요약**이다 — 화면이 중심·퍼짐을 읽고 형상을 되돌리는 데
쓴다. 묶기가 반경을 문지기로 안 쓰므로 구 시절의 폭주(반경이 크기 가중이라 큰 type 이 먼 것을
공짜로 흡수하던 것)도 함께 사라졌다.

**끝까지 안 붙은 것은 안 붙인다.** 억지로 붙이면 구성표가 거짓이 된다. 그 자리는 `POOL` 로 남고
거리로 읽힌다.

**무효화는 전파되지 않는다** — class 수정은 재계산 0, feature 변경은 그 표본만. 다만 **종합은
증분이 없다**: 축 하나만 다시 갈려도 곱이 달라진다. 값이 이미 index 에 있어 싸다.

## 읽기 — 표 하나

```
{type: {class: 개수}}      ← 저장 안 함. index 를 접으면 나온다
```

| 읽는 방향 | 뜻 | 조치 |
|---|---|---|
| 한 type 에 여러 class | 이 데이터로 안 갈림 | 병합 여부는 사람이 |
| 한 class 가 여러 type | class 안에 다른 모양 | 구성 확인 |
| 자기 class 가 소수인 type 의 표본 | 옮길 후보 | 사람이 옮김 |

**해상도 훑기도 저장하지 않는다.** 중심이 이미 있으니 조회 시점에 `d(중심ᴀ, 중심ʙ) ≤ k'` 로
묶으면 그 해상도의 그룹이 나온다(`store.Resolution`). 그래서 사용자가 `k` 를 **키우는** 방향은
재군집 없이 즉시 보이고, **줄이는** 방향만 다시 가른다.

### 읽을 때의 한계 둘

- **"여러 class" 를 그대로 "안 갈림" 으로 읽으면 안 된다.** 작은 class 가 큰 class **안**에
  들어앉은 형태는 구(球)로 못 가르므로 어느 `k` 에서도 같은 type 인데, 국소로는 갈린다
  (실측 `c151+c153` 은 한 type 인데 쌍별 1-NN 은 85%). type **안에서** 한 번 더 재야
  "정말 안 갈림" 과 "블롭이 굵어서" 가 구분된다.
- **모든 판정은 *이 데이터에 대한 진술*이다.** "c100 = c102" 가 아니라 "이 feature 로 안 갈림"
  이고, 그것이 병합 근거인지 정보 부족 신호인지는 사람만 안다.

## 자세·형상은 여기서 안 만든다 — **flow 가 만들고 정본이 든다**

추출기는 형상을 재기 전에 mask 의 무게중심과 **주축각**으로 좌표계를 정준화한다. 그 각이 곧 자세이고,
정준 극좌표에서 뜬 밴드 배치가 곧 형상 원본이다 — 둘 다 **한 패스**에서 나오므로 flow 의
`radial_profile` 유닛이 함께 낸다 ([`core/process/stream/mask/`](../process/stream/mask/profile.py)).

| 무엇 | 어디 | 바뀌면 |
|---|---|---|
| mask · pose · `radial_rle` (측정값) | **정본** — 편집과 함께 움직인다 | flow 를 다시 |
| 접기·정규화 상수·임계·계약 (잣대) | `.analysis` — config 가 정한다 | 다시 접기만 |
| type 배정·거리·종합 좌표·템플릿 (판정) | `.analysis` — 재군집마다 갱신 | 다시 묶기 |

**계산이 순수한데 왜 여기가 아닌가** — 이 층의 기준은 하는 일이 아니라 **아는 것**이다. 값을 만드는
일이 여기 있으면 같은 계산이 flow 와 분석 두 곳에 있고, 무엇보다 **분석을 돌려야만 값이 생긴다** —
flow 로 만든 정본을 그대로 쓸 수가 없다. 그래서 만들기는 flow 한 곳이고 여기는 **재는 자**다.

판정을 정본에 안 적는 이유는 위 "네 가지 정의" 가 소유한다 — *type id 는 영속 식별자가 아니다.*
정본에 적으면 재군집 한 번에 사이드카 수만 개를 다시 쓰고, 사람이 고친 것과 기계가 다시 센 것이
수정 시각으로 구분되지 않는다.

## 흐름

```
정본 순회 ─ inject ─→ feature 저장 + 잣대로 잰 값에서 정규화 상수 확정
                          ↓
                      group.build ─→ 도메인마다 cluster.fit ─→ 배정·통계를 store 에
                          ↓
                      {type: {class: 개수}} 로 읽는다
```

정규화 상수는 **확정 값**이고 잣대 좌표에서 잰다(가르기가 도는 좌표라서). 한 번 정하면 판정
대상은 그 상수를 내려받아 쓴다 — 매번 다시 구하면 구성원 하나를 옮겨도 상수가 미세하게 움직여
기준선이 조용히 흔들린다.

**산출물은 정본당 한 자리다** (`{정본}/.analysis/`). 한때 config 내용의 해시로 하위 폴더를 갈라
여러 설정의 산출물을 나란히 뒀는데, 설정을 고치면 옛 산출물을 다시 볼 일이 없었고 대신 죽은
폴더가 해시 이름으로 쌓였다. 설정이 바뀌면 계약이 바뀌고, 계약이 바뀌면 다시 뽑는다.
